## D. 已知不可测/不可靠（报告中必须标注）

1. server 侧 **per-request→engine 归因**无日志（仅 per-engine 聚合）。
2. 每请求**精确生成 token 数**不可得（客户端响应无 usage；仅聚合 counters 与 hs 文件字节代理）。
3. **真实 prefetch 队列深度**无法直接读（刻意不依赖 `_next_data` 私有量）→ E2c 为重构，已用 prefetch 容量校验。
4. **CPU affinity/NUMA 隔离实验不可做**（容器 1 核共享 cpuset）→ 只能观测 `/proc/<pid>/schedstat` 的 run-queue wait。
5. 亚秒级 histogram 区间差分不可靠（1 核下抓取器与 worker 竞争）→ 1s 为下限，附 no-scrape 对照。
6. worker↔batch 归因依赖生产序对齐（E2a 的对齐检验命中率 54.5%，因 in_order 下**生产完成序 ≠ 消费序**）→ 该分析已降级为分桶统计。

**判读（三条）**：
1. **"谁挨饿"由 docs/batch 最大值决定（剂量-反应，且可被置换反转）**：四次实验里 docs/batch 最高的 rank 恒为饥饿者
   （E1 r3=5.90→897ms；E5' r3=6.19→833ms；E6 换流后 r0=5.90→125ms、原受害者 r3 降到 4.67→0.1ms）。**支持**"请求数水平差"是受害者选择机制。
2. **均衡 docs 消除"固定受害者"（p50 897→0.1ms），但不降低总停顿率**：22.4% > 基线 14.9%；

3. **server 在全部四种配置下都未被喂满**：running p50 **0**、p90 2–3、max 5–6（slots=8）、waiting max ≤6；
   四次 run 的 **步/s 完全相同（0.8）** → 瓶颈是**共享的 client 侧取数并发**（叠加本机 1 CPU 核），不是 server 产能。

### F4 每请求延迟拆解（E1）→ 两个独立因子
| 环节 | 每请求 | 占客户端周期(407ms) |
|---|---|---|
| server 排队 | 3.8 ms | 1%（**server 无拥堵**） |
| server GPU prefill | 147.4 ms | 36% |
| server e2e 小计 | 187.6 ms | 46% |
| 客户端纯 CPU（HTTP/JSON + 19MB HS safetensors 载入 + 校验） | 119.1 ms | 29% |
| 未归因（调度/IO/线程切换） | ~100 ms | 25% |
| **客户端观测 RTT** | **406.7 ms** | 100% |

- **因子①并发不足（结构性）**：worker 用**同步** openai 客户端 → 每 worker 只有 1 个在飞请求 → 每 rank 在飞 = 2
  → 每 rank 供给上限 ≈ 2/0.407 ≈ **4.9 docs/s**；重度 rank 需求 = 5.90/1.26 ≈ **4.68 docs/s（利用率 96%，刀刃）**；
  轻度 rank 4.67/1.26=3.7（76%，故 15% 空转）；server 8 槽只被喂到 running p90=3 → **缺口在 client 侧**。
- **因子②CPU 成本（放大器）**：每请求 119ms 客户端 CPU（×8 workers≈2.2 核）+ ~100ms 未归因调度/IO，
  把周期从 server 的 188ms 拉到 407ms（2.2×）→ 直接压低每 worker 吞吐；但节点有 640 核、无节流 → **不是稀缺源**。

server 启动日志（两条 WARNING）：`max_num_scheduled_tokens is set to 4096 based on the speculative decoding settings.
Consider increasing max_num_batched_tokens ...`
- 我们未设 `--max-num-batched-tokens` ⇒ 每 engine step 可调度 token 上限 = **4096**；

## J. 两个遗留问题的定量回答

### J1 为什么"doc 负载全相同"（E5 均衡）仍有尖峰？——**ρ（需求/能力）才是判据**
ρ = 该 rank 需求( docs/batch ÷ step_time ) ÷ 能力( workers ÷ 每请求RTT )

| run | 各 rank ρ | 各 rank 慢步(>200ms)率 |
|---|---|---|
| E1 自然不均 | r0 0.821 / r1 0.916 / r2 0.935 / r3 **0.951** | 0.1% / 0.3% / 6.1% / **53.0%** |
| E5 均衡 | r0 0.940 / r1 0.948 / r2 0.937 / r3 0.933 | **37.8% / 36.7%** / 6.8% / 8.2% |
| E5' 不均衡 | r0 0.808 / r1 0.892 / r2 0.930 / r3 **0.947** | 0.3% / 2.6% / 3.2% / **54.0%** |
| E6 置换 | r0 **0.949** / r1 0.940 / r2 0.919 / r3 0.806 | **49.5%** / 12.0% / 1.5% / 0.1% |

**规律（跨 4 个 run、16 个 rank-样本一致）**：
- ρ ≲ 0.90 → 慢步 ≤ 3%（几乎不卡）
- ρ ≈ 0.92–0.95 → 慢步 6%–54%（**陡增**）
→ **均衡 doc 只是把"一个 rank 的 ρ 从 0.95 拉低"换成"四个 rank 都停在 ρ≈0.94"** ⇒ 所有 rank 都进入易卡区间，
但没有任何一个获得"余量"，所以：固定受害者消失、**总慢步率反而升到 22.4%**（无力消除尖峰）。
**要消除尖峰必须让 ρ 明显低于 ~0.9** —— 这只能靠提高能力（worker 数↓RTT）或降低需求（更小的 docs/batch），而不是"平均分配"。

### J2 stream swap 后"最高 load p50 有明显差距"？——**统计上是同一分布，p50 是刀刃统计量**
| | n | fast(<1ms) | 中间(1–200ms) | slow(>200ms) | 慢模 p25/p50/p75 | ρ | RTT |
|---|---|---|---|---|---|---|---|
| E1 rank3（重流） | 1500 | 46.3% (±2.5pp) | 0.7% | 53.0% | 1647/1962/2215 ms | 0.951 | 407ms |
| E6 rank0（同一重流） | 1500 | 49.3% (±2.5pp) | 1.2% | 49.5% | 1602/1910/2216 ms | 0.949 | 407ms |
- fast 占比差 **3.0pp < 95%CI(±2.5pp×2)** → 不显著；慢模分位、ρ、RTT **逐项相同**；
- 但**中间段只占 0.7–1.2% 的质量** ⇒ 中位数恰好落在两模之间的悬崖上：fast 46.3% 时 p50 落进慢模（≈900ms），
  fast 49.3% 时 p50 落在快模之上（≈125ms）→ **3pp 的（噪声级）差异被 p50 放大成 7×**。
- 对照：E5 rank0 是**真实**变轻（fast 60.6%、slow 37.8%、慢模中位 1549 vs 1962ms，ρ 0.940）
⇒ **结论：比较必须用"模占比 + 慢模分位 + ρ"，不能只看 p50。**

## K. server 天花板的进一步排查（E4-C/E4-D 与存储实测）

### K1 E4-C：token 预算**不是**天花板（H 节结论被否定）
| server 配置（W=8 固定） | 总 docs/s | **engine tokens/step** | engine steps/s | tokens/s | waiting 原因 | 预占 |
|---|---|---|---|---|---|---|
| budget 4096（E3_w8 对照） | 29.7 | **2609** | 7.4 | 19243 | capacity 25 | 0 |
| budget 16384 | 29.7 | **2821** | 6.8 | 19243 | capacity 22 | 0 |
| budget 32768 | 29.5 | **2821** | 6.7 | 18981 | capacity 16 | 0 |
- **开关确认生效**：server 启动日志 `'max_num_batched_tokens': 16384 / 32768`，且 `max_num_scheduled_tokens is set to 4096` 警告**消失**（0 次）。
- 但吞吐/engine 行为**完全不变** ⇒ **token 预算不是天花板**；engine 每步只吃 ~2800 token（≈4 请求），远低于任何预算。
- `num_requests_waiting_by_reason = capacity`（16–25），preemptions 0，prefix cache 命中 0% ⇒ scheduler 自认"容量不足"。

### K2 存储实测（HS 落盘/读取）
| 项 | 数值 |
|---|---|
| 文件系统 | **本地 ext4**（`/dev/mapper/openeuler-home`，非 NFS） |
| 写吞吐（600MB sync） | **1.4 GB/s** |
| 读吞吐（drop_caches 后） | **2.6 GB/s** |
| 每 doc HS 体积 | 709 tok × 6 层 × 2560 维 × 2B ≈ **21.8 MB** |
| 29 docs/s 的流量 | **≈630 MB/s 写 + 同量读**（≈写吞吐的 45%） |
⇒ 存储负载很重但**未饱和**（不构成硬天花板，但是显著的固定成本）。

### K3 新的候选天花板：spec-decode 的有效并发（正在由 E4-D 验证）
- server 启动警告原文提到"为 draft token 槽位预留"⇒ 若每请求实占 2 槽，则 `max_num_seqs=8` 的有效并发 ≈ **4**
  （与实测 ~4 请求/步、2800 tok/step、29 docs/s 完全吻合；且解释了为何提高 token 预算无效——限制在**槽位**而非 token）。
- **E4-D（进行中）**：W=8 固定、token 预算 32768，把 `--max-num-seqs` 提到 **16 / 32**。
  - 若吞吐随之翻倍（≈58/116 docs/s）⇒ **坐实"有效并发槽位"是 server 天花板**；
  - 若不变 ⇒ 天花板是 GPU 算力（prefill FLOPs）或存储/落盘路径，需继续二分。

### K4 E4-D 结果：并发槽位**也不是**天花板 —— server 天花板是"token 速率"
| server 配置（W=8 固定） | docs/s | tokens/s | engine steps/s | tokens/step | running p50/max | waiting p50/max |
|---|---|---|---|---|---|---|
| seqs=8, budget 4096（对照） | 29.7 | 19243 | 7.4 | 2609 | 3 / 7 | 12 / 25 |
| seqs=16, budget 32768 | 31.1 | 20115 | 4.5 | 4478 | 6 / 14 | 0 / 14 |
| seqs=32, budget 32768 | 29.7 | 18972 | 4.4 | 4331 | 6 / 21 | 0 / 0 |
- 并发从 3 → 6、峰值 7 → 21，排队从 25 → **0**，但**吞吐与 tokens/s 完全不变**。
- engine 每步耗时随 tokens/step 线性增长（353ms/2609、995ms/4478）⇒ **无 batching 摊销** ⇒ 瓶颈是"每 token 固定成本"。
- 定量：Qwen3-4B 每 token KV 写入 ≈ 2×36层×8KV头×128×2B ≈ **147 KB**；HS 落盘 ≈ 30 KB/token
  ⇒ 19k tok/s ≈ **2.8 GB/s KV 流量 + 570 MB/s 落盘** ⇒ 这就是 server 的硬天花板。
- **结论**：server 天花板 = **token 速率 ≈19–20k prompt tok/s（≈29 docs/s）**，
  与 token 预算、max_num_seqs、排队深度、存储吞吐（1.4GB/s 可用）、CPU、调度**均无关**。

## L. 方差假设的直接检验（E7 统一请求尺寸）与 ρ 口径更正

### L1 口径更正：容量必须用**实测 RTT**（RTT 随负载自增）
| 配置 | 实测 RTT | waiting max |
|---|---|---|
| W2 | 405–443 ms | 4 |
| W4 | 557–561 ms | 7 |
| W8 | 989–1040 ms | 16–25 |
⇒ `capacity = workers/RTT` 是**自限**的（推更多 worker 会把 RTT 抬起来）⇔ 与"server 聚合 token 速率（≈19–20k tok/s）"是同一现象。
**因此我此前用固定 RTT 算的 W≥4 的 ρ 偏低，已改用实测 RTT 重算（下表）。**

### L2 E7 结果（窄带 600–800：请求尺寸 CV 0.82 → ≈0；docs/batch 天然四 rank 相等）
| run | 请求尺寸方差 | ρ（r0/r1/r2/r3） | 慢步率(>200ms) | fast(<1ms) |
|---|---|---|---|---|
| E1 变长+不均（W2） | CV 0.82 | 0.82/0.92/0.94/**0.95** | 0.1/0.3/6.1/**53.0%** | 99.7/99.5/93.3/**46.3%** |
| **E7 窄带（W8）** | **≈0** | 0.963/0.966/0.968/0.970 | **14.3/1.2/6.2/2.8%** | 84.8/98.5/92.7/96.8% |
| E7 窄带（W4） | ≈0 | 0.946/0.944/0.946/0.947 | 12.0/10.7/0.2/19.4% | 87.2/88.5/99.5/79.7% |
| E3 变长（W8） | CV 0.82 | 0.804/0.915/0.957/0.964 | 0.2/0.3/14.3/12.5% | 99.8/99.6/85.4/86.8% |

**判读**
1. **同档甚至更高 ρ 下，统一尺寸显著更稳**：E1-r3（ρ=0.95，变长）慢步 53% vs E7 窄带（ρ=0.96–0.97，统一）慢步 1–14% ⇒ **请求尺寸方差是一阶失稳来源**（支持"高 ρ 靠压方差可稳定"）。
2. **ρ→1 仍不能完全稳定**：窄带在 W4/W8 仍有 10–19% 慢步，且**"谁慢"轮转**（无固定受害者，与四 rank ρ 相等一致）⇒ 阈值上移但未消失（Kingman ρ/(1-ρ)）。
3. **第二条等价杠杆 = 在飞请求数**：E3_w8（变长、ρ=0.964）12.5% ≪ E1-r3（变长、ρ=0.951）53% —— ρ 与方差相同、差别在每 rank 8 个在飞请求把抖动平均掉。
4. **硬墙 = server 聚合速率**（RTT 自增到 ~1s、waiting 16–25）：只能靠**加副本**突破。

## M. 最终分析：ρ / 方差 / 吞吐 的关系（回答"能否高 ρ 提效"）

| 论断 | 依据 | 结论 |
|---|---|---|
| 供给受限（ρ→1）时，**平均吞吐与方差无关** | W6/W8/W12 全为 1.31–1.32 step/s；E7/W8 统一尺寸也仅 6.1% vs 变长 6.8% | 消方差只改*分布/尾延迟*，不改均值 |
| **动态完美再平衡的增益上限 ≤6%**（W2） | 聚合需求 18.4 vs 聚合能力 19.6 docs/s；W≥6（server 受限）时为 0 | 静态均衡(E5)实测未提速（1.26→1.21 s/step） |
| **真正提速靠提高平均速率** | 加副本：step 684→350ms ⇒ ≤2×（受训练计算下界约束）；统一尺寸附带 +10%（band W8 1.46 vs E3_w8 1.32） | — |
| **残余二阶失稳源** | (a) 整数装箱 per-step 跳动（窄带仍 {5:813,6:387}，波动 19%）；(b) server 排队方差（RTT 0.41→1.0s 自增）；(c) 集合同步放大器 | ρ 实际上限≈0.95–0.96 |
| **反例：rank 级残余抖动** | E7b 四 rank ρ 均≈0.94，慢步率 0.1% vs 38.1%；ρ 最低的 r2 最稳，r3 优于 r1 | 存在与 ρ/尺寸无关的 rank 级抖动（疑 server 排队顺序），**当前最大未知** |

**pack 级请求（整包一次请求）可行性**：✅ 同时消除请求数与尺寸抖动；✅ 摊薄每请求固定开销；✅ 不需改语料；
⚠️ 需 ≤ max_model_len（含 draft 槽 → 收到 ~4000）；engine 步填满率变化；失败粒度 5 docs；需数据层重构。
**吞吐预期：不提速**（server 为 token 速率上限，E4-C/E4-D 已证预算/并发均无效）。
