# 报告：DSpark 在线训练中 FSDP2 多卡 forward 周期性尖峰的根因分析（定稿）

**问题**：dp4 + FSDP2 训练时出现**周期性 forward 尖峰**（单卡无、多卡有；周期随 server DP / train DP 变化；W↑ 或 server 副本↑ 可缓解）。
**方法**：不预设结论。把原假设 H 拆成 5 条因果边，逐边设计**可否定**实验；先做零边际成本的离线分析，再做**因果干预**（流置换/均衡/扫参/方差控制）。
**证据**：`EVIDENCE.md`（A–M 节，每条主张都指向数据文件与数字）；原始数据 `exp/<RUN_ID>/`（含 `config.txt`、`diff.patch`、每-rank JSONL）；插桩可 `snapshot/revert.sh` 一键回退。

---

## 1. 现象（参考配置：dp4、W2、prefetch4、server 单副本 dp1、700k、seed42）

| 指标 | 值 |
|---|---|
| 周期 | `load_ms` 慢步指示序列自相关 **lag2 ρ=0.96**（周期≈2 步） |
| 幅度 | 慢 rank 迟到 p50 **882ms**、p90 2294ms；ready_skew p50 **1067ms** |
| 传导 | 该步其余 rank 的 fwd 时长 **+~1.1s**（gap_before_ag2），p90 达 2.4s |
| 消失条件 | 单卡；或 W≥4–6；或 server 副本增加 |

## 2. 原假设 H（被检验对象，不作结论）

```
token 打包 → 各 rank docs/batch 不均 → server 供给不足/排队 → DataLoader starvation
        → 该 rank 晚进 forward → 其他 rank 在 FSDP AllGather 等待 → 周期性 fwd spike
```

## 3. 逐边证据

| 边 | 判定 | 关键数字（出处见 EVIDENCE.md B 节） |
|---|---|---|
| ① docs 多 → 单批生产成本高 | **支持** | worker 侧样本耗时和 **1088→2951 ms**（docs 1→8+）；collate 25→49ms；**token/批恒定**（3875–3879） |
| ② 累计 docs → prefetch 耗尽 → 断粮 | **否定** | K∈{2..32}×Δ∈{0..16} 互相关**无 Δ≥1 显著格点**；最佳全在 lag=0 且 ρ≈0 |
| ②′ 当期成本解释等待 | **否定** | `load_ms ~ docs / Σ样本延迟 / docs+tokens` 三模型 **R²≈0.013** |
| ③ 队列枯竭 → 该 rank 卡 | **形态修正** | 队列深度 p50：r0 6 / r1 5 / r2 4 / **r3 2**（cap8）；慢 rank `load_ms` **双峰**（46.3% <1ms、49.6% 1–3s）→ **慢性**而非偶发 |
| ④ 卡 → 晚进 forward | **支持** | 按 gs 与按集合序对齐**0% 标签不符**；rank3 迟到 p50 882ms，其余 0.7–5.2ms |
| ⑤ 晚到 → 他人等待 | **支持（位置修正）** | 集合调用 `ag_block≈0.1ms`、`wait_for_unshard 0.4ms`（主机侧不阻塞）；等待在 **`gap_before_ag2`**（首次消费聚合参数）：r0 1033 / r1 1058 / r2 966 ms、r3 45ms；回归 `gap ≈ 迟到量`：**slope 0.97–0.98、R²=1.00（n=400）** |

## 5. server 天花板（最终定性）

- **engine 恒定 tokens/s ≈19–20k**（budget ×8 无效、并发 ×3 无效）⇒ **token 速率天花板**，根因是每 token 的固定成本（Qwen3-4B 每 token KV 写 ≈147KB + HS 落盘 ≈30KB，engine 无 batching 摊销）。
- 客户端侧表现为 **RTT 随负载自增**：0.41s@W2 → 0.56s@W4 → **1.0s@W8**（waiting 0→7→16）⇒ `capacity = workers/RTT` **自限**。
  ⇒ 与"server 份额 = 29 docs/s ÷ dp"等价（**我此前用固定 RTT 算的 W≥4 的 ρ 偏低，已更正**）。
- 存储不是硬天花板：本地 ext4 写 1.4GB/s、读 2.6GB/s，HS 流量 ~630MB/s（≈45%）。
- 面板 A 中：预算/槽位/排队/CPU/swap/调度**均已排除**（E4-C/E4-D/E7：`schedstat` run-queue wait 0.1%、pswpout 0）。

## 6. 方差实验（E7/E7b）：能"高 ρ 稳定"吗？

| run | 请求尺寸 | 在飞/rank | ρ（四 rank） | 慢步率 | 均值 |
|---|---|---|---|---|---|
| E1 变长+不均 | CV 0.82 | 2 | 0.82/0.92/0.94/0.95 | 0.1/0.3/6.1/**53.0%** | 14.9% |
| E5 doc 均衡 | 变长 | 2 | 0.94×4 | 37.8/36.7/6.8/8.2 | 22.4% |
| **E7b 窄带** | **≈0** | 2 | 0.91/0.94/0.94/0.95 | 18.9/38.1/0.1/14.0 | 17.8% |
| E7 窄带 | ≈0 | 4 | 0.944–0.947 | 12.0/10.7/0.2/19.4 | 10.6% |
| E3 W8 | 变长 | 8 | 0.80/0.92/0.96/0.96 | 0.2/0.3/14.3/12.5 | 6.8% |
| **E7 窄带 W8** | **≈0** | 8 | 0.963–0.970 | 14.3/1.2/6.2/2.8 | **6.1%** |

**结论**
1. **在飞请求数是最强杠杆**：W2→W8 使均值慢步 14.9%→6.8%（变长语料同样下降）。
2. **压方差不能降低"总量"，只能摊平负担**：匹配 ρ 与在飞数时（W8）统一尺寸 6.1% ≈ 变长 6.8%；W2 下 17.8% 甚至略高于 14.9%。它的效果是**消灭固定受害者**（最坏 rank 53%→38%）与提高 fast 占比。
3. **ρ≈0.95–0.96 是本系统（单副本）的实际稳定上限**；ρ 上不去的原因是 server 平均速率 + RTT 自增（§5）。
4. **残余二阶失稳源（已定位）**：(a) 整数装箱的 per-step 需求跳动（窄带下 docs/batch 仍为 {5:813, 6:387}，**波动 19%**，32% 的步 ρ 临时 >1）；(b) server 排队方差（越近天花板越厚）；(c) 集合同步放大器（slope≈1）把残余抖动放大成尖峰。
5. **反例（重要）**：E7b 中四个 rank ρ 几乎相同（0.94）但慢步率 **0.1% vs 38.1%**，且 ρ 最低的 r2 最稳、ρ 更高的 r3 优于 r1 ⇒ **仍存在与 ρ、与请求尺寸无关的 rank 级抖动源**（疑似 server 排队顺序/worker 请求被服务的时序），这是当前最大未知。

## 7. 工程结论：提效 vs 稳定（回答"能否高 ρ 提效"）

- **供给受限（ρ→1）时，平均吞吐 = 每 rank 能力（或 server 份额）÷ 每步请求量，与方差无关**；消方差只改*时间分布*（尖峰→平滑）与*尾延迟*。
- 量级：W2 下聚合需求 18.4 docs/s vs 能力 19.6 docs/s ⇒ 即使"动态完美再平衡"也仅 **≤6%**；W≥6（server 受限）时为 **0**。
- **真正提速只能提高平均速率**：加 server 副本（step 684ms → 350ms，**≤2×**，受训练计算下界约束）；统一请求尺寸附带 **+10%**（band W8 1.46 vs E3_w8 1.32 step/s）。
- **提高可接受的 ρ 的价值** = 保持速度下减少资源（成本效率）+ 消除毛刺（长跑稳定）。

## 8. 方案可行性（只分析，未实施）

| 方案 | 消除 per-step 抖动 | 需要改语料 | 预期提速 | 主要风险 |
|---|---|---|---|---|
| **整个 pack 作为一个请求** | ✅ 请求数与尺寸都恒定 | ❌ 不需要 | 无（server 为 token 速率上限）；摊薄每请求固定开销 | must ≤ `max_model_len`（4096 含 draft 槽需收到 ~4000）；engine 步填满率变化；失败粒度 5 docs；需数据层重构（生成从 `__getitem__` 上移到 pack 级） |
| 恰好 N doc/包 | ✅ 需求恒定 | ✅ 需过滤/截断到 doc ≤819 token | 无 | 改变训练分布；n=5 时需把包预算收到 <6×最短 doc |
| 长度分桶（不改协议） | 部分（尺寸变均匀） | ✅ | +10% | 改变分布 |
| 加 server 副本 | 否 | 否 | **≤2×** | 占卡 |

## 9. 最终根因 / 放大机制 / 缓解

- **根因（乘性）**：① 需求侧：每步请求数 = docs/batch（token 打包不约束请求数，各 rank 4.67 vs 5.90，+26%）；② 供给侧：worker 同步客户端 ⇒ 每 rank 能力 = `workers ÷ RTT`，而 RTT 受 server token 速率上限约束（自增）。
  ⇒ 判据 **ρ = 需求/能力**：实测 **ρ≲0.90 → 慢步≤3%；0.92–0.95 → 6–54%**。
- **放大器（独立、不可被数据优化消除）**：DP 集合同步把任一 rank 的迟到 τ 变成全体 fwd 尖峰 ≈τ（slope 0.97–0.98、R²=1.00）。
- **缓解（按实测效果）**：加在飞数（W↑，最强）> 加 server 副本（同时抬高上限）> 统一定长请求（摊平 + 10%）> 静态 doc 均衡（仅消除受害者）。

## 11. 剩余不确定性（不得用推测补齐）

1. **rank 级残余抖动**（E7b：同 ρ、同尺寸下 0.1% vs 38.1%）成因未定 —— 疑与 server 排队顺序/worker 请求时序有关，**当前最大未知**。
2. server 侧 **per-request → engine 归因**无日志 ⇒ "token 速率受限"是聚合层证据（tokens/s 恒定 × 三次配置）。
3. 每请求**精确生成 token 数**不可得（响应无 usage）；HS 体积为估算（6 层×2560×2B）。
4. **真实 prefetch 队列深度**为时间戳重构（未读私有变量），仅以 prefetch 容量校验。
5. **CPU affinity/NUMA 隔离**不可做（640 核共享节点）；仅以 `schedstat`（0.1%）间接排除。
6. **GC 停顿**未直接测量。
7. **worker↔batch 精确归因**依赖生产序对齐（命中 54.5%，in_order 下生产完成序 ≠ 消费序）→ 该分析已降级为分桶统计。
8. 全部实验为**单一 seed（42）+ 单机 + 单副本 server**；平台 **run-to-run 非逐位可复现**（同配置两次 |Δloss| 0.0165）⇒ 结论仅依赖分布/统计量。
